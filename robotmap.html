The robot map

One team wires the robot. Another team writes the code. The only thing that keeps them agreeing is a single shared sheet: which motor is CAN ID 5, which breaker channel it lives on, and which way "positive" turns it. Get that sheet right and bring-up is calm. Get it wrong and you spend the first practice match asking "wait, which motor is 5?" while the arm drives itself into the floor.

Why the map exists

The contract between two teams

Think of it like a group project where one person builds the poster and another writes the labels. If nobody agreed on what goes where, the labels land on the wrong pictures. The robot map is that agreement, written down before anyone argues:

  • CAN ID - the address each motor controller and sensor answers to on the shared CAN wire. Every device needs its own. Two devices sharing an ID is like two houses with the same street number: mail goes nowhere.
  • PDH channel - which numbered breaker slot on the Power Distribution Hub feeds that motor. It tells electrical where to plug the power wire, and it tells you where to look when a motor goes dead.
  • Positive direction - which way the mechanism moves when the code sends a positive command. A gearbox mounted as a mirror image of its partner spins the opposite way, so the map records it as Inverted to cancel that out.

Fill it in once, together, and the code below writes itself. Below is a real handoff: a wiring diagram from the electrical team, a map for you to fill, and a live bring-up test that tells you the second something does not line up.

Reading the mounts: a standard gearbox runs its mechanism the intended way on a positive command, so it is Forward. Why this beats "which motor is 5?"

    
Without a map, bring-up turns into a guessing game: someone spins a motor, someone else yells "no, the OTHER one," and every fix lives only in one person's head. The shared map turns all of that into lookups. Electrical wires to the sheet, you code to the sheet, and when a mechanism misbehaves you check the sheet first instead of re-deriving it under pressure.

    
This page is a friendly version of templates/Constants.java - the one file where a real robot keeps its IDs, channels, and directions so you change a number in exactly one place. Keep your map in that file, print a copy for the pit wall, and update both the second a wire moves. Always confirm live IDs and directions with your mentor in Phoenix Tuner before a match.

Question 1

        
On bring-up the robot spins in place instead of driving straight, even though both drive motors respond. What does the robot map most likely have wrong?

        

          
          
          
        

        
The left and right gearboxes are mirror images, so one side has to be Inverted for "positive means forward." If both are set Forward, one side drives ahead while the other drives back, and the robot pivots in place. Flip the mirror-mounted side to Inverted and it rolls straight. This is exactly the direction column doing its job.

      

      

        
Question 2

        
Your teammate wired the arm's CANcoder but left it off the robot map. What breaks?

        

          
          
          
        

        
Every device that talks on the CAN bus needs its ID on the map, sensors included. If the CANcoder's ID never makes it into the code, the arm's angle reads as unknown or zero and any position control goes haywire. The map is not just for motors - it is for everything on the bus.

      

      

        
Question 3

        
Two motor controllers end up set to the same CAN ID. Why is that worse than a wrong-but-unique ID?

        

          
          
          
        

        
A CAN ID is an address, and two devices on one address is like two houses sharing a number - the bus cannot tell them apart, so messages get confused and devices can disappear. A wrong-but-unique ID is a simpler fix: the command just goes to the wrong single place, and you correct one number. This is why the map keeps every ID unique on purpose.
